## 1. 结论与证据边界

**核心矛盾不是导出器损失画质，而是把“确定性的像素绘制与变换工具”当成了“能理解造型、材质与动作的美术生成器”。**

目前的链路能稳定复现输入，但输入中的圆冠、矩形树干、平移史莱姆不会因执行更多 op 自动变成经过设计的像素美术。需要优先补齐的是：美术规格、原创模板与关键帧、材质/区域语义，以及真实的看图修正闭环。

问题分成四层，不能混为同一种“缺功能”：

| 层次 | 已发现的问题 | 应对方式 |
|---|---|---|
| 评估口径 | 不同尺寸、不同题材和不同用途的素材直接比较；整张图集色数被用于推断单帧难度 | 建立同尺寸、同视角、同用途的基线与参考清单 |
| 配方/美术输入 | 几何占位、缺少层次和关键姿势；纹理与光照未体现物体结构 | 先用已有 `pixels`、`patch_pixels`、`parts` 重做少量高质量模板 |
| 实现语义 | 色阶选择歧义、动画终态遗漏、GIF 循环设置丢失、同名动画 QA 漏检等 | 确定性缺陷先补测试再修复，不用审美问题掩盖工程错误 |
| 能力范围 | 结构化材质、局部动作模板、autotile 等缺失或不足 | 按目标素材需求扩展，不照搬通用图像编辑器功能清单 |

## 2. 真实链路：质量在哪里决定

### 2.1 当前数据路径

`recipe → palette/spec/parts → base → post/directions/anims → IndexFrame → pxl.json → sheet PNG/JSON → preview → validate`

主要职责：

| 模块 | 实际职责 | 不应期待它自动完成的事 |
|---|---|---|
| `pxl-cli/src/cmd.rs` | 加载、调度、配方执行、文件输出、调用 QA | 从素材名称推导美术设计 |
| `pxl-gen/src/shapes.rs` | 按顺序画矩形、圆、线、矩阵及描边 | 理解树叶、头发、箱体透视 |
| `pxl-gen/src/bollinger.rs` | 蒙版随机采样、镜像、补边、ramp 着色 | 自动恢复语义、可靠的人形造型、多视角设计 |
| `pxl-gen/src/noise.rs` | 周期 value noise、斑点/草色变化、内部矿簇、边缘修正 | 草地覆盖关系、可控矿脉、同一光源下的材质组织 |
| `pxl-ops/src/apply.rs`、`parts.rs`、`macros.rs` | 整数像素变换、部件合成、宏展开 | 从一张站姿推导完整跑跳动作 |
| `pxl-export/src/lib.rs` | 索引 PNG、最近邻预览、GIF | 补充造型或恢复缺失细节 |
| `pxl-qa/src/lib.rs` | 索引、几何结构、帧差及类别规则 | 判断“放进目标游戏不会违和” |

### 2.2 配方操作顺序也会改变结果

- `shapes`/Bollinger 路径先在 base 上执行 `post`，动画变换已处理的图。
- `parts` 路径需要在合成之后执行相应后处理，不能把两条路径视为天然等价。
- 每个动画帧从同一 source 生成，不是从上一帧累积。只写“再移动一格”的思路会得到错误轨迹。
- `build` 最后才做 sheet QA，此前已写出产物；单独 `gen`、`op`、`anim` 不会自动完成同一套 QA。

因此，修改计划必须明确每个新能力作用于哪一层、使用哪个坐标系、如何传播 mask/锚点，以及何时验证。

## 3. 两份报告需要修正的判断

两份报告关于“造型粗、边缘明暗不足、噪声代替材质、缺少视觉反馈”的主方向成立，但不能直接照抄功能优先级。

| 原判断/倾向 | 核对结果 | 对计划的影响 |
|---|---|---|
| 原语只有矩形/圆，因此无法画出细节 | `pixels` 和逐帧 `patch_pixels` 已能表达当前尺寸内的任意索引排列；不足主要是创作效率、模板和结构信息 | 不把新增 polygon/ellipse 当作画质提升的前置条件 |
| ramp 短，所以无法 hue shift | palette 可直接存不同色相的 RGB，ramp 是索引序列；3–4 阶也能做色相偏移，现有 palette 也不能概括为色相完全不变 | 优先修 palette 内容和使用方式，而非先写 HSV 引擎 |
| 抖动/AA 是主要画质缺口 | 对 8×8、16×16 素材，抖动可能增加噪点，AA 可能降低边缘清晰度；是否有益取决于目标风格 | 默认关闭，待对照实验显示收益后再加入 |
| 任意角度旋转缺失解释四向尖刺不能做 | 已有 `rotate90`/`flip` 可覆盖正交朝向；受光方向可能需重着色 | 四向配方现在就能做；八向和非正交动作另立任务 |
| 矿石只有散点、完全没有团簇 | `paint_ore_veins` 已把种子点扩展到四邻居；但团簇大小/轮廓和内部亮暗主要由 hash 决定 | 改进的是受控簇结构与统一光照，不重复实现已有邻域扩散 |
| 没有区域变换，宏全是整帧移动 | `shade`、部分变换已有 region；树风配方也限制了行范围；但缺少稳定的语义部位、关键帧和动作约束 | 先复用局部 op 与 parts，再补通用语义 mask |
| 整张图集数百色，所以单个小精灵不可实现 | 图集总色数不等于每帧色数；palette 接受 256 色，但文本矩阵只有 0–35 的表示范围，存在另一个真实契约问题 | 按单帧统计，不凭整表色数下结论；先修表示范围与报错 |
| 大边框、长条、字体、立绘都“不可行” | 应区分单帧尺寸限制、缺少自动编排、缺少美术输入、完全不同的渲染系统；960×540 二色边框并不需要复杂绘画 | 使用“当前未支持/不属本轮目标”，不把可绘制性与自动创作能力混同 |
| 所有 style 指标都适合硬门槛 | Jaggies、banding、pillow shading、轮廓闭合存在明显风格例外；SSIM/IoU 会惩罚合理的原创差异 | 硬约束与启发式建议分开，不能用单一分数替代人工判断 |
| 3D 烘焙对照意味着需要先实现复杂灯光 | 16×16 几何箱与 48×48、二百多色烘焙裁切不是有效的单变量对照 | 先比较同尺寸道具，3D 资产生产单列外部路线 |

另外：原报告把 slime 参考描述为低饱和灰白，本次未取得对应裁切，不能据此直接把绿色史莱姆改成灰白。应先核对参考帧、透明背景及 palette，再确定配色目标。

## 4. 根因分析

### R1：缺少目标美术规格，测试对象和“预期效果”没有对齐

参考涉及 PICO-8、不同游戏的角色/地形/UI，以及 3D 烘焙，不能共享一个笼统的“像素风”目标。相同放大倍数只是保持像素方块大小，并不会消除不同原生分辨率的影响。

- `terra-tiles` 用 16×16 对照 8×8 模板，改变了纹理的空间频率和细节预算。
- `orchard-tree` 用 32×40 对照报告所述约 48×80 树内容，造型压缩本身就影响分枝和树冠层次。
- crop 把土带画入作物，而参考土层独立；比较时混入了资产职责差异。
- 跑步对照混入头发物理、攀爬和冲刺缺失，这些属于动作/运行时覆盖，不应全部计入当前跑步静帧的风格分。

**后果：** 很容易通过加色、放大画布、添加特效“追分”，却使实际游戏中的风格更不统一。

### R2：输入是占位几何，输出却按完成美术验收

`shapes` 按绘制指令执行，并不推理体积。树冠是圆不等于树叶簇；把史莱姆画成圆再整体移动也不等于弹性动作。`shaded-crate` 的明暗面本来就是手工矩形填色，不能归功于自动光照。

**必须增加的输入：** 轮廓模板、负空间、材质区、少量受控细节点和动作关键姿势。工具负责高效编辑/复用，不应承诺 seed 自动创造这些信息。

### R3：`shade` 只有边缘规则，且缺少材质归属

它只检查顺光与背光方向的邻居是否透明。内部像素即使属于不同朝向的面也不会自动分开；两侧都暴露时加减可能抵消。

先 `outline` 再 `shade` 还可能让实体边缘的透明邻居变成轮廓像素，导致主体提亮不生效；轮廓色在某个 ramp 中时，反而可能改变轮廓。不能把两种顺序视为等价，也不应简单把所有配方顺序一律倒置。

更直接的问题是 `Palette::shift_on_ramp` 在 `BTreeMap` 中找到第一个含该颜色的 ramp 就返回：

```125:139:crates/pxl-core/src/palette.rs
    pub fn shift_on_ramp(&self, index: u8, delta: i32) -> u8 {
        if index == 0 {
            return 0;
        }
        for ramp in self.ramps.values() {
            if let Some(pos) = ramp.iter().position(|&c| c == index) {
                let len = ramp.len() as i32;
                let mut next = pos as i32 + delta;
                if next < 0 {
                    next = 0;
                }
                if next >= len {
                    next = len - 1;
                }
                return ramp[next as usize];
```

`examples/reference/shaded-crate/palette.json` 中索引 8 同时属于 `sideR` 和 `metal`。按名称顺序会优先命中 `metal`；当该像素触发位移时，可能从木质色走到金属色。`sideR` 的明暗排序也需要美术复核，不能因为字段名叫 ramp 就假定它单调。

**设计结论：** 第一步是明确 ramp/材质选择与保护规则，不是从二值轮廓自动推导“真实法线”。距离场只能提供形状启发，不能知道箱顶、木板和树叶的表面方向。

### R4：噪声提供随机性，没有提供材质结构

`generate_noise_tile` 的土/草/沙/矿通过硬编码 `cell`、斑点参数区分。草主要是噪声上部分像素提亮；矿已有小簇，但簇内各点选色缺少统一光照。

- 扩大画布不调整簇尺度，会改变材质颗粒的相对大小。
- 以画布为单位生成和修正边缘，不能表达跨 tile 草沿、矿脉与边角连接。
- 内圈放矿能保护对边检查，却可能在重复铺图后形成网格状空带；这是需要拼图验证的风险，不是本次已看图确认的结果。
- 同一 tile 的两侧 ramp 距离小，不代表两个不同 seed 的 tile 相接无缝。

需要的是“基底 → 簇/裂缝/叶片结构 → 统一受光 → 细节”的分层生成，以及独立的邻接规则。

### R5：动作靠通用变换，且存在明确语义缺陷

配方层的 `meadow-slime` 明确选择 `idle_rumble(steps=2, amp=1)`，这本来就只表达抖动，不能期待它产生挤压落地。树风虽限制行范围，也没有树枝/树冠分簇和相位关系。

库内还存在可证明的问题：

| 项目 | 源码事实 | 后果 |
|---|---|---|
| `walk_side`/`run_side` | 下半画布移位加 bob，四帧实际只有两种姿态；未实现规划里的 `leg_region` 语义 | 无法代替接触、经过、抬腿等关键姿势 |
| `blink` | 对顶部三分之一执行 `shade`，没有闭眼矩阵/眼部选择 | 名为眨眼，结果只是局部明暗，甚至无可见变化 |
| `death_dissolve` | 使用 `0..steps`，最大 `step` 为 `steps-1` | 不保证输出全透明终态 |
| random dissolve | op 子种子含 frame name，独立帧的随机采样不保证共享阈值 | 可能出现已消失像素后续重现，需新增单调性测试 |
| `spin_projectile(steps=8)` | `i / 2` 后执行 `rotate90` | 是四朝向各停两帧，不是八个朝向 |
| 宏参数 | map 解析后缺少未知参数检查 | 规划示例中的参数或拼写错误可能静默失效 |

这些修复能改善动作可信度，但不能解释所有静帧画质问题。

### R6：验收“通过”与画质“通过”不是同一个结论

默认 QA 检查 bbox 面积占画布 20%–95%、四连通块数、孤立像素及整画布归一化帧差 1%–35%。存在以下边界：

- bbox 面积不是实际像素填充率，细框也可能拥有大 bbox。
- 四连通会把合理的斜线识别为多个块；孤立像素也可能是有意高光/粒子。
- 帧差混合了位移、换色、闪白和真实变形；扩大透明边距就能降低差分比例。
- 生长状态、眨眼、受击闪白、死亡空帧不适合共享一套阈值。
- 默认对 tile 跳过角色结构检查，但没有自动补上完整的 tile 接缝检查。
- `tank`/`character` 路径与默认规则的组合方式需要核对并重构，不能以“专用规则通过”推断通用安全项一定都执行。
- sheet 构建按裸动画名去重 QA 元数据：第二个素材的同名动画可能不再参与动画 QA，即便导出 tags 已重命名。

### R7：预览与重现契约会干扰判断

- `encode_gif` 固定 `Repeat::Infinite`，无法遵守 `loop:false`；死亡、生长等一次性动作会被误看成循环。
- GIF 通过整数厘秒表达帧时长，当前 `100/fps` 截断会积累速度偏差。
- PNG 预览固定深色背景；细黑边在该背景上的对比度不等于进入游戏后的对比度。动画帧条实际宽度和返回的单帧尺寸元数据也不一致。
- build 中局部 base seed、全局 override 和输出 seed 元数据不完全一致；`gen_version` 被记录不等于真正选择旧算法。
- palette 接受 256 色，而文本矩阵只能编码 36 个索引；扩大色数之前应先定义格式兼容策略。

这些不是主造型根因，但会导致对照实验不可追溯、导出观感与数据不一致。

## 5. 目标、范围与技术路线

### 5.1 本轮目标

1. 从“同类图标占位”提升到“在指定风格约束下可复用的原创小素材”。
2. 先把 `meadow-slime`、`item-chest`、`terra-tiles` 做成可复测样板，再推广到其余七类。
3. 每个结论都能对应一份配方、一组真实 seed、一套预览和具体修改点。
4. 维持索引色、整数坐标、确定性生成与可版本化回归；不为追求一项视觉效果破坏已有契约。

### 5.2 不属于本轮的承诺

不承诺仅靠程序噪声达到商业手绘质量；不做通用肖像绘制、3D 渲染器、运行时头发物理或完整游戏 UI 系统。复杂美术允许通过原创矩阵、人工部件或合法外部资产进入流水线。外部导入和量化是后续能力，不等于自动解决美术设计。

### 5.3 最小结构语义方案

后续扩展按以下顺序，而不是一次引入 `light + AO + rim + normal` 大系统：

1. **现有配方先行：** 手写少量原创矩阵、材质区和关键帧，建立好结果的上限样板。
2. **显式 ramp：** 色阶操作可指定 ramp；共享索引无显式归属时诊断，不按名称猜材质。
3. **命名选择区：** 同尺寸二值 mask/部件区域、保护区、锚点，坐标系固定为当前帧或明确的部件局部坐标。
4. **离散面着色：** 每个面显式指定 material/ramp 和亮暗级，先覆盖箱体三面、树冠几簇，不伪装成自动法线。
5. **可选方向光：** 有显式面方向或高度信息时再计算定点亮度并映射 ramp；没有输入时只提供明确标注的启发式模式。
6. **可选修饰：** 材质轮廓、受控抖动和渐变仅在模板风格需要时启用。

mask 必须跟随对应几何变换；不能只移动像素、不移动材质区。语义层尽量作为可选辅助数据，不要求每个 `IndexFrame` 使用者都携带完整场景结构。

### Q7 / P2：由需求拉动的覆盖扩展

不作为前三个样板提升的前置条件：

- `autotile`：如果下一步就是完整地形地图，则提前到 P1；先选择并定义一种 blob/Wang 邻接语义，再做变体展开、角规则、去重与 tilemap 元数据。
- 非正交旋转：用于八向投射物等明确需求；先评估目标 8–16px 下的轮廓质量，不假定 cleanEdge 能自动保留所有细节。

- HSV/desaturate：编辑 palette 而非破坏索引材质语义，按模板验证收益。

## 8. 验收体系：硬约束、启发式、人工判断分开

### 8.1 必须失败的硬约束

索引范围、透明约定、尺寸/帧数限制、引用存在、未支持参数、mask 尺寸/坐标契约、输出元数据一致性、确定性、合法邻接关系，以及动作规格显式要求的锚点/终态。

结构检查按类别配置：角色可以约束主体连通性，粒子允许多块，死亡允许终帧为空，UI 允许稀疏，tile 允许满铺。裁切默认告警或严格模式失败，主动裁切必须显式声明。

### 8.2 先作为告警的确定性指标

- 实际用色、ramp 使用分布、显式明暗 ramp 的亮度趋势。
- 主体面积/bbox/质心、四连通与八连通两套统计、非预期孤点和轮廓厚度。
- 轮廓台阶、banding、疑似 pillow shading、边界梯度、tile 周期重复。
- 帧差同时报告整画布归一化和非透明并集归一化；空集情况独立处理。
- mask/anchor 稳定性与剪影面积曲线，按动作类型解释，不一刀切要求面积不变。

色相不要求所有 ramp 同向偏移；outline 不要求所有风格闭合；有意高光/粒子通过显式区域或类别白名单表达，不能仅凭“很亮”就放行。

亮度/色距若采用 OKLab 等浮点计算，应先作为离线诊断；要进入跨平台硬验收需规定固定实现/容差或定点方案，不能破坏当前确定性要求。

### 8.3 相对参考指标的边界

SSIM、剪影 IoU 只用于同尺寸、同视角且合理对齐的诊断，或自有素材的回归；不把“复制参考像素”作为原创目标。LPIPS/CLIP 可以研究，但未校准时不属于风格真值。小图放大到模型输入尺寸并不会创造新的语义证据。

### 8.4 视觉接受标准

建议采用 1–5 的有锚点量表，和旧报告 1–10 分分开保存，不能直接比较总分：

- 1：目标不可辨认或严重结构错误。
- 2：占位可辨认，但有明显造型/光照/动作问题。
- 3：满足规格，可用于原型，仍需局部精修。

#### B06 / P0：合法低位深 PNG 可让预览 panic（R）

生成 8×8、1-bit indexed PNG，`render` **退出 101**，在 `pxl-export/src/lib.rs` 的 `scale_rgba` 越界。`decode_rgba`/`decode_indexed` 未展开 packed 1/2/4-bit 像素，把压缩字节当作每像素索引。16-bit RGB/RGBA 的读取也缺少明确转换（S）。

**修复：** RGBA 解码明确 EXPAND/16→8；索引路径正确解包或清楚拒绝不支持位深，不得静默误读。检查解码长度和像素/放大预算。**验收：** 1/2/4/8-bit indexed、透明 PNG、16-bit、截断输入及超限尺寸均有测试；合法输入正确返回，非法输入返回 `PxlError`，不得 panic/OOM。

#### B07 / P0：小画布不能约束图元溢出与计算量（R＋S）

8×8 shapes 输入 `rect=[2147483647,0,1,1]`，debug CLI 在 `shapes.rs` 的 `x+w` **panic，退出 101**。S：圆平方、线段差值及超大遍历存在类似风险；越界非法颜色若被裁掉或被覆盖，最终像素校验也发现不了。

**修复：** 绘制前验证每条命令的颜色、算术和计算预算，先安全求画布交集再栅格化；明确允许裁切，不把底层 `set` 全局改成报错。**验收：** 极值坐标/半径、完全裁剪、覆盖掉的非法色、巨大但小交集图元均快速、可预测地返回；debug/release 不能一个 panic 一个静默空图。

#### B08 / P1：tile 身份/ramp 丢失，合法满铺图被当 sprite（S）

`make_sheet` 仅在无动画且 kind 为 tiles 时记录 tile 元数据；因此水面、破坏砖、static idle tile 均可能丢失类别。`tiles[]` 生成时使用的 ramp 未完整保存在 doc；`tile gen --variants 1` 还会标为 sprite。对应入口分别位于 `cmd.rs` 的 sheet 构建、tile 生成与文档构建。

**修复：** category、tile ramp、是否覆盖层/无缝地表随资产传播，不从动画有无/variant 数量推断。分类输入支持外部冻结约束；CLI 无外部约束时只声明检查了自报类别，不能承诺符合游戏设计。**验收：** 满铺 static tile、动态水面、破坏砖、自定义 ramp、单/多 variant 跨入口等价；UI 改成 tiles 与冻结契约冲突时失败。

#### B09 / P1：能力描述与实际宏/Schema 不一致（R＋S）

R：`schema shapes`、`schema doc` 退出 2，`schema pxl` 成功；历史 Harness 允许查询前两者，v5a/v5b 分别重复失败 2/6 次。S：宏目录已经含参数元数据，但和执行默认值脱节：

| 宏 | 目录声明 | 执行实现 |
|---|---|---|
| `tread_cycle` | bob 默认 0 | 默认 1 |
| `idle_breathe` | 默认 2 帧 | 无参 4 帧 |
| `bob` | 2 帧 | 4 帧 |
| `walk_side/run_side` | stride 2/3 | 默认 1/2 |
| `death_dissolve` | 4 帧、seed 0、pattern 含无效值 | 默认 6 帧、seed 7、bayer4 |
| `blink` | 示例仅 lid | 实际要求 x/y/w/h |

**修复：** 元数据与解析/默认值单一来源；补 shapes schema，明确 `doc` 别名或同步消费者使用 `pxl`；schema/list/build/validate 的错误码统一。**验收：** 每个目录示例可执行，“省略默认值＝显式默认值”，实际帧数一致或有参数化表达；不再立项“从零新增宏元数据”。

#### B10 / P1：组合操作重复处理与非方形旋转损失（S）

- parts 方向先 post，动画若只是 noop/shift 又追加 post，outer outline 二次扩张、ramp 二次移色；方向从已处理方向派生也类似。源码：`cmd.rs` 的 `build_sprite`。只在 compose 重建画布后重新 post，不能仅凭 parts_mode 无条件追加。
- `spin_projectile` 通过重复 cw 得到 180/270 度，每次裁回原矩形。4×2 输入 `1234/5678` 两次 cw 得 `.76./.32.`，直接 180 应为 `8765/4321`。每个目标朝向应从未裁剪 source 一次生成。
- `row_shift` 的有/无 region 两模式会忽略不同参数；`shear(axis="vertcial")` 静默按 x 执行。要校验值域及互斥组合，不只是未知字段名。

**验收：** parts＋noop 的像素不变，非幂等 post 只生效一次；矩形旋转各目标与直接变换一致；不支持参数组合/拼错枚举明确失败。parts 多级姿态不继承属于尚需明确的 local/world 契约，不直接归为已证实 bug。

#### B11 / P1：透明 palette 与着色约定不闭合（S）

`Palette::validate` 允许 `special.transparent` 非 0、非零索引 alpha=0、ramp 含 0；几何/QA 却固定以 index 0 判断透明。结果可能是“QA 有实体、PNG 不可见”，或 shade 把实体移到透明产生孔洞。

**修复：** 确定唯一透明约定并在输入层拒绝/显式规范化；区分着色 ramp 与有意擦除/闪烁操作，不禁止所有透明动画。文本格式只能表示 0–35，而 palette 允许 256 色，应在目标输出已知时早报范围错误，数组/RLE 另立格式版本。

**验收：** 透明索引、alpha、PNG/QA 实体集合一致；shade 不意外改变 alpha；35/36 边界有端到端测试，错误落到具体字段而非最终序列化。

#### B12 / P1：预览格式与时序入口不一致（R＋S）

R：`render eightbit.png -o preview.gif` 返回成功，但文件 magic 为 PNG。S：recipe build 未共享独立 anim 命令的 fps/帧数范围校验，fps 0/极大值可能产生 sheet duration 与 GIF 最低 1cs 延迟不一致。

**修复：** 按输出格式统一编码分派，不支持组合显式报错；fps/帧数上限进入公共语义校验层。**验收：** 扩展名、格式、返回元数据一致；0/1/60/61 fps 与边界帧数在各入口采用同一政策。保留已经修好的正常 fps 累积舍入和 loop 行为。

### V2.4 不再重复立项的修复与优化边界

| v1 项目 | v2 复核状态 | 后续动作 |
|---|---|---|
| Q2.1 显式/唯一 ramp | 已实现，shared index 不再按字典顺序误选 | 补 B11 的透明约定，不重写整个 hue 引擎 |
| Q2.2 未知宏参数、blink 眼区、假八朝向 | 主要修复已有测试 | B09 修目录真实性，B10 修矩形旋转/参数组合 |
| Q2.3 dissolve 首末帧与空间随机阈值 | 已实现并有单调性测试 | B02 修 QA 终态身份，不倒退终帧算法 |
| Q2.4 GIF loop、正常时长累积、PNG 帧条尺寸 | 已实现且本次测试通过 | B06/B12 是解码/输出分派/非法时序的新缺口 |
| Q2.5 同名动画 | 常规同方向场景已修，结构化身份未完成 | B03 继续，不沿用“全部完成” |
| Q2.6 类别与空终态 | 仅部分场景可用 | B02/B08 及专用规则分层 |
| static 支持 | recipe 与 sheet 已接通，doc 漏接 | B01，不从头设计 static |

优化项不应先于正确性修复：

- `shade` 仍是透明边缘邻域规则，outline 先执行会遮住主体边缘；四向旋转还旋转了烘焙高光。先显式材质/面/保护区与方向光约定，再评估距离场等启发式。
- 默认 texture seed 与 frame name 相关会重新采样；需要稳定表面纹理时显式固定 seed，再设计时间相位，不能把可重复生成误认为跨帧稳定。
- 单 tile 对边规则不保证不同 variants 相邻；先定义合法邻接/边界签名，再考虑完整 autotile。
- parts 当前仅支持有限附着语义；先写明父子 local/world 姿态及多级继承合同，再决定是否扩展骨架。
- 先把校验逻辑从巨大的 `cmd.rs` 中抽成可测试纯转换，按 B01/B03/B08 的边界逐步拆分；不为拆文件而大规模重构。
- 不新增通用 AI 图片生成调用，不引入默认抖动/AA，不扩大 MAX_DIM 来掩盖造型缺陷。性能优化用本地固定 fixture 的 P50/P95、像素预算、批量 QA 计时驱动，而不是以模型端慢响应解释 Rust 引擎性能。

#### V2.7.2 兼容策略

- 元数据增加版本与旧格式读取路径；旧数据缺少类别/身份时明确 legacy/inferred 状态，无法安全恢复则报错，不能静默跳过。
- 宏默认值与 post 修复可能改变像素/帧数；先决定修实现还是修目录，按真实合同处理，必要时提升生成版本。不要为通过测试统一重写黄金 hash。
- 严格输入拒绝、原子发布和 overwrite 行为属于可观察变化，随 CLI 契约说明；保留失败诊断能力，但拒绝把 invalid bundle 暴露为有效输出。
